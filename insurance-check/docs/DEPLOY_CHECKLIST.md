# 운영 배포 체크리스트

> **소속 GA(보험대리점)의 보험 모집 광고 사전 심의와 개인정보 처리 승인을 받기 전에는 운영 배포를 하지 않는다.**
> 이 앱은 승인 기록(`APPROVAL_*`)이 비어 있으면 운영 모드 빌드가 실패하고(`npm run build` → `scripts/check-deploy.mjs`),
> 런타임에서도 신청 폼이 잠긴다. 아래 수동 항목은 코드로 강제할 수 없으므로 담당자가 직접 확인한다.

## A. 자동 검사 (`npm run check:deploy`)

| 구분 | 항목 | 환경변수 |
|---|---|---|
| 승인 | 보험 모집 광고 사전 심의 승인일 | `APPROVAL_AD_REVIEW` |
| 승인 | 개인정보 수집·이용 문구 및 처리 흐름 승인일 | `APPROVAL_PRIVACY` |
| 승인 | 보장 분석 추가 제안 화면·동의 문구 승인일 | `APPROVAL_COVERAGE_OFFER` |
| 승인 | 처리 주체·제3자 제공 여부 확정일 | `APPROVAL_THIRD_PARTY` |
| 승인 | 통계 수치 원문 대조 완료일 | `APPROVAL_STATS_VERIFIED` |
| 고지 | 운영 주체, GA 명칭·등록번호, 설계사 성명·등록번호, 연락처, 주소, 개인정보 보호책임자, 처리 주체(점검/보장분석), 제3자 제공, 보유기간(점검/보장분석), 광고 심의필 번호, 처리방침 시행일 | `config/requirements.json` 참고 |
| 인프라 | HTTPS 서비스 URL, Supabase URL/anon/service role 키, `APP_SECRET`, `PII_ENCRYPTION_KEY` | 〃 |

승인일은 `YYYY-MM-DD` 형식만 인정된다. 승인 문서(심의필, 승인 메일 등)는 별도로 보관한다.

## B. 수동 확인 (배포 전 매번)

### 문구·준법
- [ ] `lib/content.ts`의 모든 문구가 심의 받은 버전과 **글자 단위로 일치**한다 (수정 시 재심의)
- [ ] 통계 4건(2025년 말 숨은보험금 약 10조 3,000억원 / 2025년 지급 약 80만 건·약 3조 2,470억원 / 청구 1건당 평균 약 404만원)을
      [금융위원회 2026-07-07 보도자료](https://www.fsc.go.kr/po010103/87270) 원문과 대조했다
      (개발 환경에서는 fsc.go.kr 접속이 막혀 **원문 직접 대조는 하지 못했다**. 2026-10에 같은 발표를 보도한 복수 언론
      — 뉴시스·헤럴드경제·비즈니스포스트·미디어펜·디지털데일리·시사저널 — 의 수치가 일치함을 교차 확인했다.
      특히 404만원이 보도자료 본문의 수치인지 언론의 환산값인지 원문에서 확인. 원문 대조 후 승인일 기록)
- [ ] 평균 환급액(약 404만원) 바로 아래에 "개인별 예상 환급액 아님 · 실제 지급된 청구 건의 평균" 표기가 붙어 있다
      (E2E `landing.spec.ts`가 자동 검사. 2026-10 운영자 요청으로 평균값을 메인 수치와 같은 크기의 블루 카드로 강조함 →
      평균값 노출·강조 자체를 GA 광고 심의에서 허용하는지 반드시 확인)
- [ ] 상황별 예시 카드가 실제 지급 사례가 아닌 일반 예시임이 표시되고, 병원비 미청구 카드는 숨은보험금 통계와 별개로 표기된다
- [ ] "모든 고객 환급", "대상자 선정", "금융위원회 인증·위탁" 등 오인 표현이 없다 (E2E `landing.spec.ts`가 일부 자동 검사)
- [ ] 고객 후기·실적·자격·제휴 로고를 임의로 추가하지 않았다. 후기는 `/admin/reviews`에서 **게시 동의 기록이 있는 실제 후기만**
      등록·승인하고, 지급 금액은 지급 확인 서류가 있을 때만 입력한다 (후기 게재 자체도 광고 심의 대상인지 GA에 확인)
- [ ] 사회적 증거 문구("다른 사람들은 이미 확인하고 있는 보험금", "약 80만 건 지급")가 건수 기준·전국 공식 집계 표기와 함께 심의를 받았다
- [ ] 공감 섹션의 상황 예시(질문·확인 포인트)가 예시 표기와 함께 심의를 받았다 (문구 수정 시 재심의)
- [ ] 후기 캡처 이미지는 프로필 사진·실명·전화번호·대화 상대 정보가 모두 가려졌는지 공개 승인 전에 다시 확인한다.
      고객 게시 동의 기록(일시·방법·동의 범위)은 별도로 보관하고, 동의 철회 시 `/admin/reviews`에서 즉시 삭제한다
- [ ] 실제 운영 지표 공개(`PUBLIC_METRICS_ENABLED=1`)는 심의 승인 후에만 켠다. 내부 테스트 신청은 신청 상세에서 '내부 테스트'로 표시해 집계에서 뺀다
- [ ] 해지환급금 안내에 보장 상실·손실 가능성이 표시되고, 해지를 권유하는 표현이 없다
- [ ] 보험금 청구 안내와 손해사정(지급 판단·손해액 산정) 업무가 구분되어 있다
- [ ] 푸터의 승환계약(기존 계약 해지 후 신계약) 유의 문구를 GA 기준 문구로 확인했다

### 개인정보
- [ ] 개인정보 처리방침(`/privacy`)을 GA 승인 버전으로 확정했고 시행일을 설정했다
- [ ] 처리 주체가 설계사 개인인지 GA 법인인지 확정하고 `PRIVACY_CONTROLLER`/`COVERAGE_PROCESSOR`에 반영했다
- [ ] 제3자 제공(예: GA 본사, 제휴 보험사)이 있다면 `THIRD_PARTY_PROVISION`에 제공받는 자·목적·항목·보유기간을 기재했다
- [ ] 동의 문구를 바꿨다면 `lib/config.ts`의 `*_CONSENT_VERSION`을 올렸다
- [ ] 보유기간 경과 데이터 파기 작업(`supabase/schema.sql` 하단 예시)을 스케줄링했다
- [ ] 삭제 요청의 본인 확인 절차(예: 신청 번호로 회신 전화)를 정했다

### 보안·인프라
- [ ] 기존 DB에는 `supabase/schema.sql`을 다시 실행해 `ic_reviews` 테이블과 `ic_leads.is_test` 컬럼을 추가했다
      (이전 구조의 `ic_reviews`(claim_type 컬럼)를 이미 만들었다면, 등록된 후기가 없는 상태에서 `drop table public.ic_reviews;` 후 다시 실행)
- [ ] `supabase/schema.sql` 실행 후 `select * from pg_policies where tablename like 'ic_%';` 결과가 **0행**
- [ ] service role 키는 서버 환경변수에만 있다 (`NEXT_PUBLIC_` 접두사 없음, 클라이언트 번들에 없음)
- [ ] `ic_staff`에 실제 담당자만 등록, 역할 최소 권한(CSV 내보내기는 admin만)
- [ ] Supabase Auth 비밀번호 정책·MFA 설정
- [ ] 엣지/WAF 레이트리밋 적용 (앱 내 레이트리밋은 인스턴스별 메모리라 보조 수단)
- [ ] 백업·복구 절차 확인

### 측정·광고
- [ ] 광고 플랫폼 전환은 `form_submit_success`(`is_conversion: true`)만 사용하도록 태그 구성
- [ ] 광고 픽셀(Meta 등)을 추가할 경우 동일한 동의 절차를 거치고, 이벤트 파라미터에 개인정보·건강정보를 넣지 않는다
- [ ] 계약 단계 수치는 관리자 입력만 사용한다 (보험사·GA 시스템 연동은 별도 승인 후)
