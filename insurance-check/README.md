# 내보험 통합 점검 (가칭) — 광고 랜딩 + 상담 CRM MVP

미청구·숨은 보험금, 과오납 보험료·해지환급금 **확인 방법 안내** 랜딩과, 신청 접수·별도 동의 기반 보장 분석 상담을 관리하는 CRM입니다.

> ⚠️ 이 디렉터리는 상위 저장소(lawsel.kr 법률 AI)와 **독립된 Next.js 앱**입니다. 상위 앱의 빌드·배포·`/admin`과 섞이지 않도록
> 상위 `tsconfig.json`과 `.vercelignore`에서 제외되어 있습니다. 실제 운영 시에는 별도 저장소/Vercel 프로젝트로 분리하는 것을 권장합니다.

## 스택

상위 저장소 스택을 그대로 따릅니다 — Next.js 15 (App Router) · React 19 · TypeScript 5.7 · Tailwind CSS 3.4 · Supabase.
UI는 shadcn/ui 규칙(cva + `cn`, 소스 복사 방식)으로 작성한 `components/ui/*` 와 lucide-react 아이콘을 씁니다.
(shadcn CLI 최신판은 Tailwind v4 기준이라, 기존 3.4 스택과 맞추기 위해 컴포넌트를 소스로 포함)

## 실행

### Windows: 더블클릭으로 실행
1. Node.js LTS(20 이상)를 설치합니다 — https://nodejs.org
2. `insurance-check` 폴더의 **`start-demo.bat`**을 더블클릭합니다.
   - Node.js 확인 → 설치(처음 1회) → 데모 설정(처음 1회) → 서버 실행 → 준비되면 브라우저 자동 열기
   - 창에 표시되는 **관리자 비밀번호**로 http://localhost:3100/admin/login 에 로그인합니다.
   - 창을 닫으면 서버가 꺼집니다. 이미 실행 중이면 브라우저만 엽니다.
   - 인터넷에서 받은 파일이라 "Windows의 PC 보호" 또는 "게시자를 확인할 수 없습니다" 경고가 뜰 수 있습니다. **추가 정보 → 실행**을 누르세요.
   - 항상 데모 모드로만 실행되며, `.env.local`이 운영 모드면 실행을 멈춥니다.
   - 이 파일은 한글 Windows 명령 프롬프트용으로 CP949·CRLF로 저장되어 있습니다(`.gitattributes`로 변환 방지). GitHub 웹에서는 한글이 깨져 보일 수 있지만 실행에는 문제없습니다.

### 직접 명령으로 실행

```bash
cd insurance-check
npm install
npm run setup:demo              # 데모용 .env.local 생성 + 관리자 비밀번호 출력 (이미 있으면 유지)
npm run dev                     # http://localhost:3100  ·  관리자: http://localhost:3100/admin/login
```

| 명령 | 내용 |
|---|---|
| `npm run setup:demo` | 데모 모드 `.env.local` 생성 (APP_SECRET·관리자 비밀번호 랜덤) |
| `npm run dev` / `build` / `start` | 개발 / 빌드(배포 게이트 포함) / 실행 (포트 3100) |
| `npm run typecheck` | `tsc --noEmit` |
| `npm test` | 단위 테스트 (vitest) — 검증·마스킹·암호화·세션·CSV·영업대상 규칙 |
| `npm run lint` | ESLint (Next.js core-web-vitals + TypeScript 규칙). `next build`도 같은 규칙으로 검사한다 |
| `npm run test:e2e` | E2E (Playwright, 서버 실행 중이어야 함) — 사용자 여정·관리자 권한·axe 접근성·반응형 |
| (포함) `apply-flow.spec.ts` | 세 유형 카드 실제 클릭·탭 → 다음·이전 → 제출 → 완료 → 보장 분석(동의/거절/건너뜀) → CRM → CSV, 입력 오류·연타·네트워크 오류·새로고침·뒤로가기 |
| (포함) `crm.spec.ts` | 관리자 전 메뉴, 화면 이동 중 필터·목록 중복 없음, 편집 저장 유지, 테스트 신청 필터·영업 대상 제외, 로그아웃 |
| `DEMO_ADMIN_PASSWORD=… npm run verify:deployed` | 배포 사이트 점검(`tests/e2e/release-check.spec.ts`) — 사례 3개 우선·2개 접힘, 사례별 유형 자동 선택, 심사·지급 문구, 모바일 2단계 폼, 데모 신청 → CRM 조회. `E2E_BASE_URL`로 대상 변경. 운영 모드면 신청 테스트는 건너뜀 |
| `npm run check:deploy` | 운영 배포 필수 항목·승인 기록 점검 |

E2E는 레이트리밋(IP당 10분 5건)에 걸리지 않도록 **서버를 새로 띄운 뒤** 실행하세요.

## 모드

| | 데모 (`APP_MODE=demo`, 기본) | 테스트 (`APP_MODE=staging`) | 운영 (`APP_MODE=production`) |
|---|---|---|---|
| 저장소 | 서버 메모리 (재시작 시 초기화) + **가짜 시드 데이터**(데모고객NN / 010-0000-NNNN) | Supabase Postgres — 모든 신청을 **테스트 신청**(`is_test`, 운영 지표 제외)으로 저장 | Supabase Postgres (service role, 서버 전용) |
| 표시 | 상단 '데모 모드' 배너, 폼·관리자·레코드에 '데모' 배지 | 상단 '테스트 모드' 배너, '테스트' 배지, 완료 화면 안내 | 없음 |
| 신청 폼 | 시연용으로 동작 (실제 개인정보 입력 금지 안내) | 인프라 6개 + `APPROVAL_DB_VERIFIED` + **DB 자동 점검 통과** 시 접수 | 운영 정보·인프라·**GA 승인 기록이 모두 있어야** 열림 + DB 자동 점검 통과 |
| 관리자 로그인 | `DEMO_ADMIN_PASSWORD` + 역할 선택(관리자/상담사/열람) | Supabase Auth 이메일·비밀번호 + `ic_staff` 역할 | 같음 |
| 운영 주체 정보 | 미설정 값은 `[설정 필요: …]`로 표시 (가짜 값 생성 안 함) | 같음 (요구하지 않음) | 필수 |
| 분석 태그(GA4·Meta) | 로드 안 함 | 로드 안 함 | 측정 ID + 방문자 동의 시에만 로드 |
| 검색엔진 | noindex | noindex | index (`/admin`, `/api`, `/apply` 제외) |

**Preview 전용 테스트 신청**: Vercel 환경변수 `PREVIEW_TEST_SUBMISSIONS=1`을 **Preview에만** 넣으면, Vercel이 자동으로 주는
`VERCEL_ENV=preview` 배포에서만 테스트 모드로 동작한다(APP_MODE 값과 무관). Production 배포(`VERCEL_ENV=production`)에서는 이 값이 있어도 무시되고,
`APP_MODE=staging`도 운영 기준으로 잠긴다. 접수가 잠겨 있으면 Preview·로컬에서만 폼 아래에 **미완료 설정의 변수 이름**을 보여 준다(값은 표시 안 함,
Production에서는 표시 안 함). 테스트 신청은 `is_test=true`로 저장되어 CRM에 '테스트' 배지, CSV에 '테스트 신청' 열, 운영 지표 제외.
CRM 상세 필터의 '테스트 신청'(포함/제외/테스트만)으로 구분하며, **보장 분석 영업 대상 목록은 테스트 신청을 기본으로 제외**한다.
`STAGING_ADMIN_EMAIL`·`STAGING_ADMIN_PASSWORD`를 주면 `apply-flow`·`crm`·`staging-db` 스펙을 테스트 모드 배포(실제 DB)에도 그대로 돌릴 수 있다.

**DB 자동 점검** (`lib/server/db-check.ts`, 관리자 → 환경설정에서 결과·다시 점검): 실제 키로 데이터를 바꾸지 않고 확인한다 —
키 종류(서버 키가 비밀키인지, 공개 키 자리에 비밀키가 없는지), 공개 키로 신청·직원 조회/수정 차단, 서버 키로도 신청 삭제·감사로그 수정 불가,
02-hardening 칼럼 존재, 활성 관리자 1명 이상. 하나라도 실패하면 신청 API가 503으로 저장을 멈춘다(통과는 5분·실패는 30초 캐시).
DB 내부 설정(RLS·트리거·규칙)은 SQL Editor에서 `supabase/verify.sql` 점검표로 사람이 확인하고 날짜를 `APPROVAL_DB_VERIFIED`에 적는다.

**신청 저장 규칙**: 연락처는 서버에서 AES-256-GCM으로 암호화(`phone_enc`) + HMAC 해시(`phone_hash`, 중복 감지) + 마스킹(`phone_masked`)만 저장한다.
동의는 항목별로 여부·문구 버전·시각(`privacy_consent_at`, `marketing_consent_*`, `third_party_consent_*`, 철회 시 `marketing_withdrawn_at`)을 남기고,
브라우저가 폼마다 만든 제출 키(`idempotency_key`, DB 고유 인덱스)로 더블클릭·재전송을 한 건으로 묶는다.

**비밀키 노출 방지**: `npm run build`(check-deploy)가 모든 모드에서 `NEXT_PUBLIC_` 변수에 비밀값으로 보이는 이름·값·Supabase 비밀키가 있거나,
`SUPABASE_SERVICE_ROLE_KEY`에 공개 키 / `SUPABASE_ANON_KEY`에 비밀키가 들어 있으면 빌드를 중단한다. Supabase 접근 코드는 모두 `server-only`.

**실제 DB 연결 E2E**: 테스트 모드 배포에서
`E2E_STAGING=1 E2E_BASE_URL=<주소> STAGING_ADMIN_EMAIL=… STAGING_ADMIN_PASSWORD=… npx playwright test staging-db --project=desktop`
(DB 점검 통과 → 배너·태그 없음 → 사례 버튼 신청 → 같은 제출 키 재전송 1건 → CRM 조회·마스킹·동의 기록·연락처 복호화). 테스트 데이터만 사용(이름 '테스트검증', 010-0000-04xx).

**실제 Preview 자동 검증** (`.github/workflows/insurance-check-preview-e2e.yml`): Vercel이 Preview 배포를 마치면 GitHub Actions가 그 주소로
사전 점검(`scripts/preview-preflight.mjs` — 모드·잠김·미완료 설정 이름) → 실제 신청·DB·CRM(`staging-db`, `crm`) → 유형·입력·동의(`apply-flow @preview`, PC+모바일)
→ 화면 크기 5종·오류·권한(`viewports`, `errors`)을 돌린다. Production 배포·운영 주소는 대상에서 제외한다.
필요한 저장소 Secrets: `VERCEL_AUTOMATION_BYPASS_SECRET`(Vercel → Deployment Protection → Protection Bypass for Automation),
`STAGING_ADMIN_EMAIL`, `STAGING_ADMIN_PASSWORD`. 없으면 Vercel 로그인 화면(HTTP 302)에서 멈추고 그 사실만 보고한다.

**접수 잠금 원칙**: 잠금(`submissionEnabled=false`)은 **실제 전송만** 막는다. 유형 선택·입력·동의·이전/다음·신청 버튼 같은 화면 조작에 연결하지 않는다
(과거 잠금을 fieldset `disabled`로 걸어 Preview에서 카드·입력칸이 눌리지 않는 문제가 두 번 있었다 — `apply-flow`의 '입력'·'잠김' 테스트가 재발을 막는다).
잠긴 상태에서 올바르게 입력하고 신청하면 "지금은 신청을 접수할 수 없어요" 안내만 띄우고 아무것도 보내지 않는다. 서버도 잠김이면 503.
실제 DB를 쓰는 모드에서는 폼이 화면을 띄운 뒤 `GET /api/status`로 접수 가능 여부를 다시 확인한다(접수 API와 같은 기준: 설정 + DB 자동 점검).
잠겨 있으면 Preview·로컬에서만 폼 위와 잠김 안내 아래에 **미완료 설정 이름·실패한 DB 점검 항목·지금 보는 배포(브랜치·커밋·주소)**를 보여 준다
(값·키는 표시 안 함, Production 배포에서는 진단 없음). Vercel 배포 주소는 만들어질 때의 환경변수에 고정되므로, 설정을 바꾼 뒤에는 새 배포 주소에서 확인한다.

## 랜딩 원칙 (2026-10 개편)

- **외부 조회 사이트로 나가는 CTA를 주요 동선에 두지 않는다.** 히어로·통계·유형·절차·신청·하단 CTA·헤더에는 내보험찾아줌 링크가 없고,
  공식 서비스를 직접 무료로 이용할 수 있다는 사실과 텍스트 링크는 **FAQ(`#faq-official`)와 푸터**에만 둔다. 헤더의 '공식 조회 안내'는 이 FAQ로 이동한다.
  (운영 모드에서 접수가 잠긴 경우의 안내 문구에는 예외적으로 공식 링크가 있다.) E2E가 이 규칙을 검사한다.
- CTA: 히어로·통계 하단·하단 CTA·헤더 → 점검 유형 선택, 유형 카드·공감 카드·후기 하단·절차·모바일 고정 → 같은 신청 폼(선택 유형 유지). E2E가 모든 CTA의 도착지를 검사
- **통계 오도미터** (`components/motion/Odometer.tsx`, 계산은 `lib/odometer.ts`)
  - 화면 진입 시 한 번만 rAF로 easeOutCubic 감속, 자리별 세로 롤링(기계식 계기판 방식: 아래 자리가 9→0으로 넘어갈 때만 윗자리 이동) 후 공식 수치에 정확히 정지, 은은한 블루 하이라이트
  - 모든 자리를 처음부터 렌더해 너비 고정(레이아웃 흔들림 없음), 화면 숫자는 aria-hidden + sr-only 실제 텍스트
  - SSR·JS 실패·`prefers-reduced-motion`에서는 최종 수치를 그대로 표시
  - 통계 섹션의 링 그래픽은 장식이며 시점별 추이를 나타내지 않는다(화면에 명시)
- 섹션 진입 Fade Up(`components/motion/Reveal.tsx`)은 화면 밖 요소에만 적용 → JS가 없어도 내용은 항상 보임

## 사용자 여정

1. `/` 랜딩 — 히어로 → 스토리 카드 3 → 공식 통계(발표 기관·발표일·원문 링크) + 후킹 CTA → (실제 후기: 동의·승인된 것만) → 절차 3단계 → **단일 신청 폼**(신청 직전 신뢰 안내·운영 주체) → FAQ → 하단 CTA → 푸터
   - 모든 CTA는 같은 신청 폼으로 이동하며 고른 유형을 유지한다. 스토리 카드에서 고른 유형은 연락처 단계로 바로 들어간다
     (연락처 단계 상단에 고른 유형과 한 줄 설명·'변경' 버튼, 유형 단계에서는 고르면 한 줄 설명·해지환급금 고지 표시)
   - 신청 폼은 2단계(점검 유형 → 이름·휴대전화 + 필수 동의 + 신청, 한 화면). 카드·CTA에서 유형을 골랐으면 1단계를 건너뛴다.
     **이름·연락처·유형만** 받는다(희망 시간은 서버에서 '시간 무관'으로 기록, 메모 없음)
   - 동의: 개인정보 수집·이용(필수) / 제3자 제공(`THIRD_PARTY_PROVISION`이 설정된 경우에만 별도 필수) / 마케팅(선택, 기본 해제). 보장 분석 상담은 신청 완료 후 별도 선택
   - 완료 화면은 서버 저장 성공 응답 이후에만 표시, 운영 연락처(`CONTACT_PHONE`)·운영시간 안내
   - 모바일 하단 고정 CTA는 히어로 CTA·각 섹션 CTA·신청 폼·하단 CTA가 보이는 동안, 그리고 입력창 포커스(키보드) 중 숨김. 팝업 없음
2. 신청 → `/apply/complete` 신청 완료 + **보장 분석 별도 제안** (신청 완료 후에만 노출)
3. A: `/apply/coverage` 목적·항목·연락 방법·처리 주체 명시 + 미체크 선택 동의 → `/apply/coverage/complete`
4. B: `/apply/done` — 서버 호출 없이 종료, 추가 신청 토큰 폐기 (영업 DB로 넘어가지 않음)
5. `/privacy` 처리방침, `/privacy/withdraw` 동의 철회·삭제 요청

## 관리자 (`/admin`)

- 미들웨어(서명 쿠키 검증) + 각 페이지·API에서 역할 재검증 (심층 방어). 세션은 HttpOnly·SameSite=Strict 쿠키, 8시간
- **상담 DB**: 신청번호·접수일·UTM·유형·고객명·마스킹 연락처·희망 시간·보험금 점검 상태·보장 분석 동의·보장 분석 상태·다음 연락·담당자·메모 / 필터·검색(이름·신청번호·전화번호 해시)·정렬·인라인 상태 변경
- **보장 분석 영업 대상**: 별도 동의 O + 철회·삭제 요청 없음만. 미동의 고객은 영업 상태로 변경 불가(서버 규칙 + DB CHECK 제약)
- 보험금 점검 상태와 보장 분석 상태는 독립 필드. 계약 단계는 관리자만 입력
- **중복 신청 감지**: 30일 내 같은 연락처(HMAC 해시) → 최초 신청번호 표시, 유효 제출 집계에서 제외
- **연락처 원문 열람**: 상담사·관리자만, 매 열람 감사로그
- **CSV 내보내기**: 관리자만, 마스킹 연락처만, 수식 주입 방지, 감사로그
- **광고 성과**: UTM별 방문 → 유형 선택 → 신청 시작 → 유효 제출 → 별도 상담 동의 → 상담 완료 → 계약
- **철회·삭제 요청**: 마케팅/보장 분석 철회는 즉시 반영, 삭제는 본인 확인 후 완료 시 식별정보 파기
- **후기·지급 사례**: 메시지 원문 또는 개인정보를 가린 캡처 이미지 등록(상담사·관리자, 승인 대기), 공개 승인·중단·삭제는 관리자만. 실제 운영 지표와 랜딩 공개 여부 표시
- **감사로그 / 환경설정·배포 체크리스트**(관리자 전용, 값은 노출하지 않고 설정 여부만)

## 관리자 화면 구현 주의

- **관리자 화면의 `<Link>`는 모두 `prefetch={false}`.** 프로덕션 프리페치가 상세·감사·성과 페이지를 서버 렌더하면 실제로 열지 않은 화면이 '열람'으로 감사로그에 남는다 (E2E로 회귀 검사)
- **콘솔 레이아웃을 `<Suspense>`로 감싸지 말 것.** 감싸 두었을 때 같은 경로의 쿼리 이동(고객 상세 패널, 상태 칩)이 로그인 직후 몇 초간 중단(RSC 요청 ERR_ABORTED)되는 문제가 있었다 (E2E로 회귀 검사)
- 로그인·로그아웃 후에는 `window.location.assign`으로 전체 이동한다 (세션 쿠키가 바뀌므로 라우터 캐시를 쓰지 않음)

## 보안·개인정보 설계

- 브라우저에는 관리자 키·연락처 원문·인증 토큰이 내려가지 않음 (service role 키는 서버 전용, `server-only` 가드)
- 연락처: AES-256-GCM 암호화 저장 + HMAC 해시(중복·철회 매칭) + 마스킹 표시
- 수집 최소화: 이름·연락처·유형·UTM(동의 문서 `claim-2026-10-16.v2`). 병력·증권·주민등록번호 미수집
- 공개 API: 동일 출처 검사, IP 레이트리밋, 입력 크기 제한, 허니팟·최소 체류시간, 멱등 키(중복 제출 방지)
- 보장 분석 동의는 신청 직후 발급된 **서명된 영수증 토큰**(2시간)으로만 가능 — 타인 신청에 동의를 붙일 수 없음
- 철회 요청 응답은 일치 여부와 무관하게 동일 (타인 신청 여부 탐색 방지)
- 보안 헤더: CSP(프로덕션 `unsafe-eval` 제거), HSTS, frame-ancestors none, nosniff
- RLS: 모든 `ic_*` 테이블 RLS ON + 공개 정책 없음 (`supabase/schema.sql`), service_role도 필요한 권한만(신청 삭제 불가·감사로그는 추가/조회만), 감사로그는 수정·삭제·TRUNCATE 금지 트리거, 동의·파기·후기 공개 규칙은 DB 제약으로도 강제

- Meta 픽셀: 운영 모드 + `NEXT_PUBLIC_META_PIXEL_ID`(숫자) + 방문자 동의 후에만 로드. `PageView`와 저장 성공 시 표준 이벤트 `Lead`만 보내며 파라미터 없음(이름·연락처·유형 미전송)
- 당근 비즈니스 광고 전환 추적은 미구현 — 당근에서 발급하는 공식 스크립트·가이드를 받은 뒤 같은 방식(동의 후 로드, `lead_submit_success`만 전환)으로 추가
- **광고 전환은 `lead_submit_success`만** (`is_conversion: true`). 클릭·시도는 전환이 아님

### CTA 문구 A/B

광고 URL에 `?cta=a~d`를 붙이면 메인 CTA(히어로·하단·모바일 고정) 문구가 바뀌고 탭 세션 동안 유지된다. 기본은 A.

| 안 | 문구 |
|---|---|
| A (기본) | 나도 무료 점검 시작하기 |
| B | 혹시 놓친 보험금 확인하기 |
| C | 내 보험에서 확인할 항목 알아보기 |
| D | 무료 보험금 점검 상담 신청하기 |

- 같은 값을 `utm_content`에도 넣어(예: `?cta=b&utm_content=cta_b`) CRM·성과 화면에서 안별 신청 수를 비교한다
- 안별 노출 수가 충분히 쌓이기 전에는 어느 안이 낫다고 판단하지 않는다(현재 데이터 없음)

- 개인정보·건강정보는 어떤 이벤트 파라미터에도 넣지 않음 (E2E에서 페이로드 검사)
- UTM은 세션 첫 진입 값만 보존, referrer는 origin만 저장
